## What was built

`engine/cosmicmass/analysis/batch.py`. A job is one definition on one scene: the scene's settings with the law block replaced. Each job is an ordinary run of the engine, stamped like any other, in `results/<scene>/<definition>/<run-id>/` (the layout `results/T1.4/L0/` already uses, and the one the layout test allows).

- **Resumable at two levels.** A finished job is skipped the next time, as long as its settings and the engine commit are the same. A stopped job resumes from its checkpoint (E7) and gives the same files as if it had not been stopped.
- **Parallel:** `--workers N` processes on one machine; `--shard k/n` takes every n-th job, for n machines (a CI matrix).
- **A time limit** (`--time-limit`): the running jobs stop at their next step with a checkpoint, for CI jobs that are cut after a fixed time.
- **A refused job does not stop the batch.** What the engine refuses (a law it does not know, a moving body with zero inertia) is recorded with its error as `refused`; anything else that goes wrong is `failed` and is run again the next time.
- **`timing`**: a few steps of every job, nothing written, to size the budget. **`index`**: the table of a batch.

The two formats it reads (announced in the team chat for T2.1 and T1):

```json
{"definitions": [{"id": "L1b+perp-Sh", "law": {"id": "L1b", "direction": "perpendicular", "inertia": "Sh"}}]}
{"scenes": {"T1.1": {"scenario": "...", "universe": {}, "bodies": [], "numerics": {}}, "T0.2": "path/to/settings.json"}}
```

```bash
python -m cosmicmass.analysis.batch definitions.json scenes.json --timing 20                 # size the budget
python -m cosmicmass.analysis.batch definitions.json scenes.json --workers 4                 # run, or take up again
python -m cosmicmass.analysis.batch definitions.json scenes.json --shard 3/8 --time-limit 19800   # one CI machine
python -m cosmicmass.analysis.batch definitions.json scenes.json --index                     # the table
```

## Choices (labelled)

1. **The state of a batch is not a result.** One small JSON file per job in `.batch/` (ignored by git). The results are the stamped run folders; nothing is written beside them, as the layout test requires.
2. **A job is recognised by its settings and the engine commit.** Change either and it runs again. So a batch started on one commit is not silently finished on another.
3. **The scenario name of a job is `<scene>/<definition>`**, which is what puts it in its folder. The stamp says the same.
4. **`checkpoint_every` is added to the numerics of each job** (1000 by default). It is in the stamp, and it does not change the result (E7).

## The timing run (exploratory; not a result)

Made with a **provisional** list of the 102 definitions (5 readings, 2 signs, 4 directions, 3 inertias, without the 18 cells of D45), all at lambda = 1, written in a throwaway script: the real list and its ids are T2.1's. Two scenes: T0.2 as the gate runs it (200 bodies, 10,000 steps) and the Earth-moon pair of T0.1a over one period. Four steps of each T0.2 job and forty of each pair job were timed, on one core of the session's machine (2 cores).

| Scene | Seconds per step (smallest, median, largest) | Estimate for one job | For the 102 definitions |
|---|---|---|---|
| T0.2 (200 bodies, 10,000 steps) | 0.0064, 0.0081, 0.0136 | about 82 s (largest 136 s) | **2.3 hours** on one core |
| a pair (about 6,300 steps) | 0.00055, 0.00070, 0.0012 | about 4.6 s (largest 8 s) | 8 minutes on one core |

No definition was refused in its first steps on either scene.

**The budget this suggests** (rough, and only as good as its two assumptions below):

- One pass of the grid: T0.2 (2.3 h) plus six pairs (about 0.8 h): **about 3 hours on one core**.
- With the angle sweep of D44 on every definition (six angles): about 19 core-hours. On the four cores of a GitHub runner that is about 5 hours, inside one CI job; in 8 shards, well under an hour each.
- The plan's fallback (the sweep only for definitions that conserve, a shorter T0.2) is **not needed** on these numbers.

**What the estimate assumes, and may get wrong:**

1. *The first steps are typical.* For the pair, every definition was guessed at the same 6,283 steps, because the first step is the same. Under a strong Composer force the adaptive step will shorten and a job can take many times longer; the Earth and the moon are neutral, so this pair shows none of it. **The charged pairs of T1 (a proton and an electron, for instance) at lambda = 1 are where the cost can grow**, and where a job may never finish its orbit. The time limit and the checkpoints are there for that; the batch should be given a limit per job when the scenes exist.
2. *T0.2 runs a fixed number of steps*, so its cost is known; its 200 bodies make it 30 times the cost of all the pairs together.
